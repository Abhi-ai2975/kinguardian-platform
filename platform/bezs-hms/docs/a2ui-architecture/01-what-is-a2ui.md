# 1. What is A2UI?

## The problem it solves

Normally, when you build a "Create Patient" form in React, you write actual
`.tsx` code:

```tsx
function CreatePatientForm() {
  return (
    <form>
      <label>Gender</label>
      <select name="gender">...</select>
      <label>Birth Date</label>
      <input type="date" name="birth_date" />
      <button type="submit">Create</button>
    </form>
  );
}
```

That's fine for one form. But drgodly has **dozens** of FHIR resources
(Patient, Practitioner, Appointment, Encounter, Observation, Condition,
MedicationRequest, …), each with several sub-forms (a Patient alone has 10
sub-steps: names, identifiers, telecom, addresses, …). Hand-writing a React
component for every one of those would mean:

- Hundreds of near-identical `.tsx` files.
- Every small change (add a field, tweak a label) requires a code change,
  a PR, a deploy.
- An AI chat assistant that wants to "show the user a form" would need to
  somehow ask a developer to write one, in real time, which is impossible.

## The idea: describe the UI as data, not as code

A2UI flips this around. Instead of writing:

```tsx
<select name="gender">...</select>
```

...you write **JSON** that *describes* a select field:

```json
{
  "type": "TerminologySelect",
  "id": "gender",
  "properties": {
    "label": { "literalString": "Gender" },
    "valueType": { "literalString": "code" }
  }
}
```

A single, generic React component (called the **Renderer**, see
[02-component-catalog-and-rendering.md](./02-component-catalog-and-rendering.md))
knows how to turn `{"type": "TerminologySelect", ...}` into a real,
interactive dropdown. It doesn't matter whether this JSON came from a static
file on disk or was generated on the fly by an AI model — as far as the
Renderer is concerned, it's just JSON describing a UI.

This is the same idea as HTML itself (a `<select>` tag is "data" describing
a widget that the browser knows how to render), just one layer up: instead
of a fixed vocabulary of ~100 HTML tags, A2UI has its own vocabulary of ~45
domain-specific components (`TextField`, `DatePicker`, `RepeatableGroup`,
`FileUpload`, `SlotPicker`, `TerminologySelect`, charts, tables, and so on)
tailored to building healthcare forms quickly.

## Where the JSON comes from — two modes

drgodly actually has **two** different sources for this JSON, and it's
important to know which one you're looking at:

### Mode A — "Workflow" mode (the one this repo mostly uses)

A human developer writes a JSON file once, ahead of time, describing a
multi-step wizard (e.g. `create_patient.json`). This JSON is committed to
the repo like any other source file. Nothing is generated by an LLM at
render time — the LLM (if used at all) only picks *which* workflow to start,
based on what the user typed (e.g. "register a new patient" → triggers the
`create_patient` workflow). Once started, the UI schema for each step is a
static file. This is **deterministic** — the same input always produces the
same form.

This is what [03-workflow-engine.md](./03-workflow-engine.md) documents in
depth, and what all of today's GraphQL migration work touched.

### Mode B — "Legacy push" mode

An external agent can also push UI updates live over a message stream (see
`ServerToClientMessage` / `beginRendering` / `surfaceUpdate` in
[02-component-catalog-and-rendering.md](./02-component-catalog-and-rendering.md)).
This is the more "generative" mode where a model could, in principle,
compose a novel UI turn by turn. In this codebase it exists as underlying
machinery in the message processor, but the workflow system (Mode A) is
the one actually driving every real screen today.

## A tiny worked example

Take the simplest possible A2UI screen: a text field and a button.

**The JSON (this is the entire "UI"):**

```json
{
  "id": "root",
  "type": "Column",
  "properties": {
    "children": { "explicitList": ["name_field", "submit_btn"] }
  }
}
```
```json
{
  "id": "name_field",
  "type": "TextField",
  "properties": { "label": { "literalString": "Your name" } }
}
```
```json
{
  "id": "submit_btn",
  "type": "Button",
  "properties": {
    "child": "Submit",
    "action": { "name": "say_hello" }
  }
}
```

**What happens when the browser sees this:**

1. `Renderer` looks up `component.type` ("Column") in `DEFAULT_CATALOG`
   (see [catalog.ts](../../src/modules/client/ai-hub/a2ui/rendering/catalog.ts))
   and finds the real `Column` React component.
2. `Column` renders its two children (`TextField`, `Button`) the same way,
   recursively — each one is looked up in the same catalog.
3. When the user clicks the button, the `Button` component doesn't know or
   care what "say_hello" *means*. It just calls
   `processor.dispatch({ userAction: { name: "say_hello", context: [...] } })`
   — a generic event.
4. Something listening for that event (in this repo: a React hook like
   `useEmrDispatch`) decides what "say_hello" means: usually, "send this to
   `/api/workflow/submit`".

This separation — **the component tree only knows how to render itself and
emit named events; a separate layer decides what those events mean** — is
the single most important idea in the whole system. It's what lets the same
`Button`/`Form`/`TextField` components be reused across 40+ completely
different workflows without any of them containing workflow-specific logic.

Continue to
[02-component-catalog-and-rendering.md](./02-component-catalog-and-rendering.md)
to see exactly how that dispatch mechanism and the component catalog work,
in code.
